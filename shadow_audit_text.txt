Shadow-AI — Forensic-Grade Engineering Audit Report

Repository: github.com/RishuBurnwal/Shadow-AI  |  Audited commit: main (HEAD, latest as of audit date)  |  Audit date: 15 July 2026

Auditor: AI Senior Software Architect / Systems Reliability Review

1. Executive Summary

Shadow AI is an Electron desktop assistant that captures live screen and audio, transcribes speech via Google Gemini Live (cloud) or local Whisper (offline), and answers through a multi-provider LLM fallback chain (Groq → OpenRouter → OpenAI → Perplexity → NVIDIA → Gemini). The codebase is small, readable, and reasonably well-organized for its size (~1.1 MB of source), with genuine engineering care visible in the provider-fallback and updater logic.

However, the audit found that the two things the user most cares about in a "live conversational assistant" — reply latency and speech-to-text accuracy — are both actively hurt by specific, fixable architectural choices, not by fundamental technology limits. Two Critical, four High, five Medium, and three Low/Optimization issues were identified. None require a rewrite; all are addressable incrementally.

Highlights:

The app requests a full spoken AUDIO response from Gemini on every turn and then throws that audio away — while gating the actual (fast) text answer behind that unused generation finishing. This is very likely the single biggest source of perceived reply delay.

The local (offline) Whisper path is fully batch: it silently waits ~1.5 seconds after you stop talking, then transcribes the whole utterance in one call with no partial/interim results — this is what reads as "sluggish" or "slow" STT.

Voice-activity detection everywhere in local mode is a simple RMS energy threshold, not a real VAD model, so quiet endings/beginnings of words get clipped or missed in anything but a quiet room.

API keys are stored as plaintext JSON on disk instead of using Electron's OS-level credential encryption.

2. Audit Scope & Methodology

The full public repository was cloned and read file-by-file: main.py (launcher), forge.config.js, package.json, src/index.js (main process/IPC), src/storage.js (persistence), src/utils/*.js (gemini.js, providerRouter.js, providerEnv.js, localai.js, cloud.js, window.js, passthrough.js, prompts.js, renderer.js), src/audioUtils.js, src/components/*, and the test suite. Findings below are grounded in the actual source, with file and line references, not generic boilerplate.

This report focuses first on the two problems explicitly raised — (a) reply latency / "answer only after the question truly ends, but instantly after that" and (b) speech-to-text speed/accuracy — and then covers the remaining full-stack findings (security, testing, code quality, infra) required for a complete audit.

4. Deep-Dive: Why Replies Feel Late (and how to make them instant)

This section walks through the live-answer pipeline end-to-end, in the order audio actually flows, to show exactly where time is being spent unnecessarily.

4.1 Cloud path (Gemini Live + Groq/OpenRouter/etc.)

Today's flow, as implemented in src/utils/gemini.js:

1. Renderer captures mic/system audio, chunks it into 100 ms PCM frames, base64-encodes each, and sends it over ipcRenderer.invoke to the main process (renderer.js: setupLinuxMicProcessing, setupAudioCapture).

2. Main process forwards each chunk to session.sendRealtimeInput({ audio }) on a Gemini Live session opened with responseModalities: [Modality.AUDIO] and proactivity: { proactiveAudio: true } (gemini.js:624-626).

3. Gemini streams back inputTranscription text as the user speaks — this part is already fast and incremental (gemini.js:577-584).

4. Critically, the code only calls sendToAnswerProvider(transcription) — the function that actually asks Groq/OpenRouter/etc. for the answer — when message.serverContent.generationComplete fires (gemini.js:589-595).

if (message.serverContent?.generationComplete) {
    if (currentTranscription.trim() !== '') {
        sendToAnswerProvider(currentTranscription);
    }
}

generationComplete signals that Gemini has finished generating its own spoken AUDIO reply — audio the app never plays back (there is no audio-output consumption anywhere in gemini.js; only inlineData is referenced when sending images, never when receiving audio). The comment left in the code even confirms the intent:

// DISABLED: Gemini's outputTranscription - using Groq for faster responses instead
// if (message.serverContent?.outputTranscription?.text) { ... }

So the app deliberately avoids using Gemini's answer, but still pays the full latency cost of Gemini synthesizing one, because the trigger for "start the real (fast) answer" is tied to the finish of that unused generation. This is the architectural root cause of "late reply."

4.2 Local (offline) path — Whisper + Ollama

src/utils/localai.js implements its own VAD and calls Whisper only after silence is confirmed:

const VAD_MODES = {
  VERY_AGGRESSIVE: { energyThreshold: 0.02, speechFramesRequired: 2, silenceFramesRequired: 15 },
};
let vadConfig = VAD_MODES.VERY_AGGRESSIVE;

With 100 ms frames arriving from the renderer, silenceFramesRequired: 15 means the app waits 1.5 seconds of confirmed silence after the last word before it even starts transcription. Only then does it call whisperPipeline(float32Audio, ...) once, on the entire concatenated buffer (localai.js:157-180) — there is no interim/partial transcript shown while this runs, and no chunked/streaming decode. On a CPU-only machine (device: "auto" silently falling back when no GPU/WebGPU backend is available) a multi-second utterance can take several more seconds to transcribe. That combined "1.5s VAD wait + N-second batch decode" is what reads as "STT is slow."

The VAD itself is a plain RMS energy threshold (localai.js:65-78), not a trained voice-activity model. In a quiet room this is fine; with any background noise (fan, keyboard, other people) it either free-runs (thinks you're still "silent" while you speak softly) or false-triggers, both of which degrade transcript accuracy independent of the model used.

4.3 Recommended target architecture

To get "listen fully, then reply instantly, never late":

Decouple end-of-turn detection from LLM-answer generation. Do not gate the answer call on Gemini's own (unused) audio generation completing.

For the cloud path: stop requesting Modality.AUDIO from the Gemini Live session entirely if the audio is never played back, or, if the SDK requires it, trigger sendToAnswerProvider on turnComplete / the transcription-side end-of-turn signal rather than generationComplete, so the fast Groq/OpenRouter answer starts the instant the user stops talking — not after Gemini finishes a spoken reply nobody hears.

For the local path: replace the RMS-threshold VAD with a proper lightweight VAD model (e.g., Silero VAD, which runs comfortably in real time on CPU and is far more robust to noise), and drop silenceFramesRequired to ~400-600 ms (a natural pause length) once the VAD is trustworthy enough not to false-trigger on short breaths.

Move from "accumulate whole utterance → one batch Whisper call" to chunked/streaming transcription: transcribe in rolling ~2-4 second windows with overlap as audio arrives, show interim (greyed-out) partial text immediately, and finalize/correct once VAD confirms end-of-speech. This removes the "dead air" the user perceives as lag, because something appears on screen within a second of speaking, not only after the whole turn is transcribed.

Evaluate Meta's SeamlessM4T / SeamlessStreaming as an alternative to Whisper for the local path — SeamlessStreaming is purpose-built for simultaneous (chunk-by-chunk) speech translation/transcription with much lower first-token latency than batch Whisper, at the cost of a larger model footprint and more complex runtime integration (it is not currently packaged for transformers.js the way Whisper is, so it would likely need a separate Python sidecar process communicating with Electron over IPC/WebSocket, similar to how SystemAudioDump is already shelled out to on macOS).

Give every provider fetch call in providerRouter.js an explicit timeout (e.g., AbortController with 8-10s) so a stalled network request cannot silently make a reply "late" with no user feedback.



5. Detailed Findings

F-01 — Gemini Live forced to generate an unused AUDIO response, gating the real answer

Severity: Critical    Affected files: src/utils/gemini.js (lines 568, 589-595, 624-626, 586-587)

Root cause:

The Live session is configured with responseModalities: [Modality.AUDIO] and proactivity.proactiveAudio: true, but no code path plays or otherwise consumes the returned audio (outputTranscription handling is explicitly commented out as "DISABLED"). The only trigger for sending the transcript to the fast LLM answer path (sendToAnswerProvider) is the generationComplete event, which fires only once Gemini finishes synthesizing that unused audio.

Reproduction steps:

Start a Live session and speak a short question.

Observe (or log timestamps around) the delay between the user finishing speaking and update-response first firing in the renderer.

Compare against the delay between turnComplete and generationComplete in the console log dump at gemini.js:574.

Expected behavior:

The Groq/OpenRouter answer should begin streaming within a few hundred milliseconds of the user finishing their sentence.

Actual behavior:

The answer is delayed by however long Gemini takes to internally synthesize a full spoken audio response that the app never plays back.

Risk / impact:

This is the most visible, most complained-about symptom ("assistant feels slow") and is entirely self-inflicted — it costs real seconds per turn for zero user-facing benefit.

Recommended fix:

Switch the trigger for sendToAnswerProvider to the earliest reliable end-of-user-turn signal available (turnComplete, or an incremental "user stopped speaking" activity-end event) instead of generationComplete.

If the SDK/model combination requires an output modality, request the lightest one that still exposes turn boundaries, or explicitly cancel/interrupt generation once the input turn is complete.

Add a debug timer around this path so a regression here shows up in logs/tests, not just in "it feels slow" bug reports.

Implementation status: 

Not started.



F-02 — API keys stored as plaintext JSON on disk

Severity: Critical    Affected files: src/storage.js (DEFAULT_CREDENTIALS, setApiKey, writeFileSync)

Root cause:

setCredentials()/writeFileSync() serialize the credentials object (Gemini, Groq, OpenRouter, OpenAI, Perplexity, NVIDIA keys) directly to a JSON file with fs.writeFileSync and no encryption. Electron ships safeStorage specifically for this (OS keychain-backed encryption on macOS/Windows/Linux).

Reproduction steps:

Run the app, add any provider API key via the in-app manager.

Inspect the resulting file in the userData directory.

Observe the key is stored as clear, readable text.

Expected behavior:

Secrets at rest should be encrypted using the OS credential store (Keychain / DPAPI / libsecret) via Electron's safeStorage API.

Actual behavior:

Any local malware, another user on a shared machine, or a backup/sync tool with file access can read all configured provider API keys directly.

Risk / impact:

A leaked key can rack up billing on the user's provider account or be used to exfiltrate whatever that provider account has access to.

Recommended fix:

Wrap all credential read/write paths in storage.js with safeStorage.encryptString / safeStorage.decryptString.

On first run after the fix, detect legacy plaintext credentials and migrate them (encrypt-in-place) rather than losing them.

Continue redacting keys from logs/diagnostics as already done — that protects logs, not the credential file itself.

Implementation status: 

Not started.



F-03 — Local Whisper transcription is fully batch, no streaming/partial output

Severity: High    Affected files: src/utils/localai.js (processVAD, transcribeAudio, handleSpeechEnd)

Root cause:

Audio is buffered in speechBuffers during isSpeaking and only concatenated and passed to whisperPipeline() once, after silence is confirmed. No interim transcript is produced or shown while the model runs.

Reproduction steps:

Enable local/offline mode.

Speak a longer sentence (8-10 seconds).

Observe the UI shows nothing until the entire sentence has been both silence-confirmed AND fully decoded by Whisper.

Expected behavior:

Partial transcript text should appear on screen within roughly a second of speaking, refining as more audio arrives.

Actual behavior:

The screen stays blank/idle for the full duration of speaking plus VAD wait plus decode time, which reads as unresponsiveness.

Risk / impact:

Users perceive the assistant as frozen or broken during longer utterances, and cannot tell if capture is even working.

Recommended fix:

Switch to rolling-window transcription: run Whisper (or a faster model) on ~2-3s overlapping windows as audio streams in, displaying interim text; re-run/correct on the full utterance once VAD confirms end-of-speech.

Alternatively adopt a purpose-built streaming ASR engine (see F-04/roadmap) that natively emits partial hypotheses.

Implementation status: 

Not started.



F-04 — End-of-speech wait is ~1.5s before transcription even begins (local mode)

Severity: High    Affected files: src/utils/localai.js:26 (VERY_AGGRESSIVE mode), :94-104

Root cause:

silenceFramesRequired: 15 combined with 100 ms audio frames means 1.5 continuous seconds of below-threshold audio must pass before handleSpeechEnd() (and therefore transcription) is triggered at all.

Reproduction steps:

Speak a short question in local mode and stop.

Time from your last word to "Transcribing..." appearing in status.

Expected behavior:

End-of-turn should be detected within a natural pause (300-500 ms) without cutting off trailing words.

Actual behavior:

There is a fixed ~1.5s dead zone after every utterance before anything happens.

Risk / impact:

Directly causes the "answers late" complaint in local/offline mode; compounds with F-03's batch-decode delay.

Recommended fix:

Lower silenceFramesRequired once a more accurate VAD (F-05 fix) is in place, so a shorter, safer silence window does not cause false cutoffs.

Make the threshold configurable/adaptive rather than a single hardcoded preset.

Implementation status: 

Not started.



F-05 — RMS energy-threshold VAD is not a real voice-activity model

Severity: High    Affected files: src/utils/localai.js:22-28 (VAD_MODES), :65-78 (calculateRMS/processVAD)

Root cause:

Speech/silence classification is a single root-mean-square amplitude check against a fixed threshold per preset. It cannot distinguish speech from other non-silent noise (fan, music, typing) and misses quiet speech below threshold.

Reproduction steps:

Enable local mode in a moderately noisy room.

Speak a sentence with a brief natural pause in the middle.

Observe either a false "speech ended" mid-sentence, or background noise never letting silence be detected.

Expected behavior:

Speech boundaries should be detected using acoustic features trained to distinguish voice from noise, robust across environments.

Actual behavior:

Transcripts get truncated mid-sentence, or extra noise gets appended/transcribed as garbage text, both of which look like "STT is not working properly."

Risk / impact:

Directly causes the "speech-to-text not done properly" complaint; also indirectly worsens latency because false triggers waste a Whisper call.

Recommended fix:

Replace the RMS threshold with Silero VAD (small ONNX model, runs in real time on CPU, already compatible with the transformers.js / onnxruntime stack already in use) or an equivalent trained VAD.

Keep the current RMS check only as a cheap pre-filter to skip Silero inference on pure silence, for efficiency.

Implementation status: 

Not started.



F-06 — Deprecated ScriptProcessorNode used for audio capture instead of AudioWorklet

Severity: High    Affected files: src/utils/renderer.js:371,404,434 (createScriptProcessor)

Root cause:

ScriptProcessorNode has been deprecated by the Web Audio API spec in favor of AudioWorkletNode. It runs audio processing callbacks on the main JS thread, which is shared with UI rendering and IPC calls.

Reproduction steps:

Open the app during a session with both mic and system audio active.

Interact with the UI (drag window, open a menu) while speaking.

Watch for audio glitches or increased response jitter under UI load.

Expected behavior:

Audio capture/processing should run off the main thread so UI activity cannot introduce audio dropouts or added latency.

Actual behavior:

Under any main-thread load (rendering, IPC, GC pauses), onaudioprocess callbacks can be delayed or skipped, corrupting or dropping chunks of the very audio being transcribed.

Risk / impact:

Intermittent, hard-to-reproduce transcription glitches that look random but are actually load-dependent — a classic "works fine when idle, breaks under use" bug.

Recommended fix:

Migrate capture to an AudioWorkletProcessor running in the dedicated audio rendering thread; pass PCM frames to the main/renderer thread via its port instead of onaudioprocess.

This also removes the deprecation warning Chromium/Electron will eventually escalate.

Implementation status: 

Not started.



F-07 — No timeout on hosted-provider fetch calls

Severity: Medium    Affected files: src/utils/providerRouter.js

Root cause:

streamWithFallback() and the underlying per-provider fetch calls do not set an AbortController-based timeout, relying entirely on the OS/network stack default (which can be very long or effectively infinite on a stalled connection).

Reproduction steps:

Expected behavior:

A stalled provider should fail over to the next provider within a bounded, short time (e.g., 8-10s).

Actual behavior:

A single hung request can make the assistant appear to "never reply," with no visible error and no fallback triggered.

F-08 — Answer-pipeline state is module-level global, not session-scoped

Severity: Medium    Affected files: src/utils/gemini.js:36 (currentTranscription), :59 (messageBuffer), groqConversationHistory

Root cause:

These variables live at module scope and are mutated by callbacks tied to whichever Live session is currently active. On reconnect (attemptReconnect) or if two session lifecycles ever overlap briefly, stale state from a previous connection can bleed into a new one.

Reproduction steps:

Force several rapid reconnects (kill network briefly, restore).

Inspect whether transcript text from the pre-reconnect turn ever gets concatenated into the post-reconnect turn.

Expected behavior:

Each Live session's transcription/answer state should be isolated and reset atomically at session boundaries.

Actual behavior:

Best case, an occasional garbled transcript after reconnects; this is a correctness risk, not just style.

Risk / impact:

Wrap this state in a small per-session object/class instantiated per initializeGeminiSession() call, threaded through the callbacks via closure instead of shared module scope.

Recommended fix:

Not started.

F-10 — Zero automated test coverage of the audio/VAD/transcription pipeline

Severity: Medium    Affected files: test/*.test.js (only provider-router, provider-env, and contract tests exist)

Root cause:

The three existing test files verify provider priority/fallback, .env sync, and status classification — genuinely useful, but none touch gemini.js's audio handlers, localai.js's VAD/resampling math, or renderer.js's chunking.

Reproduction steps:

Run npm test and read the file list/describe blocks.

The most latency- and correctness-sensitive code path (audio → VAD → transcript → answer) should have unit coverage, especially resample24kTo16k (pure math, easy to test) and processVAD (pure state machine, easy to test).

Regressions in exactly the area users complain about (STT speed/accuracy, reply timing) can ship undetected.

Risk / impact:

Add unit tests for resample24kTo16k with known input/output sample arrays, processVAD state transitions with synthetic RMS sequences, and a mocked-session test asserting sendToAnswerProvider fires on the corrected end-of-turn event (see F-01) rather than generationComplete.

F-13 — Base64 + request/response IPC per 100ms audio chunk adds avoidable overhead

Severity: Optimization    Affected files: src/utils/renderer.js:386,419,449 (ipcRenderer.invoke with base64 data)

Root cause:

Each 100ms PCM chunk is base64-encoded (~33% size inflation and CPU cost) and sent via ipcRenderer.invoke, a full request/response round trip awaited inside the audio callback, rather than fire-and-forget.

Reproduction steps:

Profile renderer CPU/IPC time during an active session with both mic and system audio streaming.

Expected behavior:

Audio chunk delivery to the main process should be as low-overhead as possible, since it sits directly in the critical latency path.

Actual behavior:

Extra CPU/serialization cost per chunk, and unnecessary await coupling in the audio callback, both nibble away at the "instant" feel.

Risk / impact:

Switch to ipcRenderer.send (fire-and-forget) for audio chunks, or use a MessagePort/SharedArrayBuffer transfer for zero-copy raw bytes instead of base64 text.

Recommended fix:

Not started.

F-14 — Whisper backend device selection is unmanaged ("auto")

Severity: Optimization    Affected files: src/utils/localai.js:131-134 (pipeline(..., { dtype: 'q8', device: 'auto' }))

Root cause:

device: "auto" is left to @huggingface/transformers to decide, with no logging of what backend was actually selected and no explicit WebGPU/GPU preference.

Reproduction steps:

Run local mode on a machine with a capable GPU and check whether inference is actually using it, versus silently running on CPU.

Actual behavior:

On many machines Whisper silently runs on CPU when it could run faster on GPU, worsening the exact "STT is slow" complaint.

Risk / impact:

Log the resolved device after pipeline() initializes; explicitly try device: 'webgpu' first with a CPU fallback, surfacing the choice in diagnostics (launcher option 8).

6. Prioritized Fix Roadmap

Phase 1 — Immediate (this week): fixes the reported "late reply" and "bad STT" symptoms directly

F-01: Decouple answer trigger from Gemini's unused audio generation.

F-04 + F-05: Swap RMS VAD for Silero VAD; shorten silence wait once reliable.

F-03: Move local Whisper to rolling-window/partial transcription.

F-02: Encrypt stored API keys with safeStorage.

Phase 2 — Near-term (2-3 weeks): robustness

F-06: Migrate to AudioWorklet.

F-07: Add provider fetch timeouts.

F-08: Scope answer-pipeline state per session.

F-13: Reduce IPC/encoding overhead for audio chunks.

Phase 3 — Ongoing hygiene

F-09/F-10: Real lint gate + unit tests for VAD/resample/answer-trigger logic.

F-11/F-12: Gate verbose logging behind a debug flag.

F-14: Explicit GPU backend selection + diagnostics logging for Whisper.

Phase 4 — Optional strategic bet

Evaluate replacing/augmenting Whisper with SeamlessStreaming for the local path, as a separate Python sidecar process, if Phase 1-2 latency work still leaves local mode noticeably behind the cloud (Gemini) path.

7. Closing Notes

None of the findings above point to a fundamentally broken design — the provider-fallback system, the reconnection logic, and the .env synchronization are all solid, tested engineering. The latency and STT-quality issues are concentrated and traceable to a small number of specific lines (the generationComplete gate, the fixed-threshold VAD, and the batch-only Whisper call), which is good news: they can be fixed incrementally, in the order given in Section 6, without destabilizing the rest of the app.

A companion document ("Shadow-AI Fixing Plan and Implementation Prompt") accompanies this report with step-by-step implementation guidance for every finding above, written so it can be handed directly to an engineer or an AI coding agent to execute.
