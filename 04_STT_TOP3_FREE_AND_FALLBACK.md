### Why this order, not accuracy-only

Nemotron is the best _model_, but the highest integration risk — if it fails to initialize (unsupported hardware, missing runtime, model download blocked), the app needs somewhere to land that isn't a total STT outage. Moonshine is the practical middle ground: still meaningfully faster than Whisper, but such an easy integration (same pipeline call, different model ID) that it's a safe second attempt. Whisper is deliberately last and non-negotiable as the final fallback — it's the one guaranteed to work, since it's what's already running today.

### Deliberately left out of the "free top 3" (see File 1's earlier version)

Deepgram Flux and AssemblyAI Universal-Streaming are excellent — genuinely lower latency than any local option, with built-in turn detection — but they're paid cloud APIs, which doesn't fit "free" or a no-signup open-source default. If you still want to wire in Deepgram as an _optional_ extra tier for users who bring their own key (you already have one), that's a separate, additive integration — not part of this free fallback chain. Keep it as a 4th, opt-in option layered on top, not mixed into the free chain's ordering.

## Fallback chain — how it should actually work in code

Mirror the pattern used for LLM providers in `providerRouter.js` (see File 5) rather than inventing a new one:

1. **On app start / local-mode activation**, attempt to load engine 1 (Nemotron). Wrap the load in a try/catch with a timeout (model downloads can hang on a slow connection — don't let this block app startup indefinitely).
2. **On load failure or a timeout**, log which engine failed and why (reuse the same `logLatency`/structured-logging pattern already in the codebase, so this is visible, not silent), then attempt to load engine 2 (Moonshine).
3. **On engine 2's failure**, fall back to engine 3 (current Whisper) — this one should not be allowed to fail silently either, but if it does, surface a clear in-app message ("local transcription unavailable") rather than the app just going quiet, since a user mid-interview needs to know the tool has stopped working, not guess.
4. **Once an engine is loaded successfully, keep using it for the rest of the session** — don't re-attempt higher-priority engines mid-session (that would add latency and risk); only re-attempt the full chain on next app start or explicit user retry.
5. **Runtime inference failures** (not load failures — e.g., a single call throws) should be handled separately from load failures: retry once on the _same_ engine (transient errors happen), and only fall through to the next engine in the chain if the same engine fails repeatedly within a short window (e.g., 3 failures in 30 seconds) — otherwise a single flaky inference call would cause unnecessary engine-switching mid-conversation.

This is the same shape as the multi-key LLM rotation in File 5 — load-time failure vs. runtime failure are handled differently there too, for the same reason: not every failure means "abandon this option," some just mean "retry."

## Validation update (2026-08-12)

Nemotron is not a drop-in for this Electron/Transformers.js process; NVIDIA's official model card uses the NeMo Python runtime and a cache-aware streaming script. Moonshine's official ONNX model is compatible with Transformers.js, and the installed v3.8.1 runtime exports Moonshine support. No default engine was changed yet: the repository has no golden-audio benchmark proving a quality/latency win on supported hardware. Add Moonshine only after that small benchmark exists; keep Whisper as the shipped fallback. Official references: [Nemotron model card](https://huggingface.co/nvidia/nemotron-speech-streaming-en-0.6b), [Moonshine ONNX model card](https://huggingface.co/onnx-community/moonshine-base-ONNX).
